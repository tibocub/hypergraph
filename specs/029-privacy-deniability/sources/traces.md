# 029: what an Electron + Bare + Pear browser leaves on disk

All sources accessed 2026-11-21. "Source date" means the page's own date or, for source code, the
last commit on the file (main branch). "main" means I read the file at main on 2026-11-21 and did not
pin a commit. **[unverified]** marks claims I could not check against a primary source.
**[inference]** marks a conclusion I drew from code without running it.

## Short answer

- An Electron session without `persist:` keeps nearly all *per-site* storage in memory: cookies,
  HTTP cache, Local/Session Storage, IndexedDB, Cache Storage, Service Workers, code cache, the
  per-partition GPU caches, Network Persistent State, TransportSecurity, Trust Tokens, Shared
  Dictionary, and blob spill files.
- It does **not** keep the *app-wide* files in memory. These still go to `sessionData`:
  `Local State`, the shared `Preferences` file, the global GPU caches (`ShaderCache`,
  `GrShaderCache`, `GraphiteDawnCache`, `GPUPersistentCache`), `Dictionaries/`, and
  `Crashpad/`. Two of them matter:
  1. **In-memory sessions write to the same `Preferences` file as the default session**
     [inference from source].
  2. **The global GPU shader caches don't depend on the partition.** To stop them, pass
     `--disable-gpu-shader-disk-cache`.
- An app can't stop some OS-level traces: SRUM per-app byte counts on Windows, swap/pagefile,
  hibernation, Prefetch and Amcache, and the systemd journal on Linux. The only workable plan is
  this: stay quiet on disk, keep the hidden data in the vault, and tell users that full deniability
  needs full-disk encryption plus OS settings.
- Pear (`pear-runtime`) writes only under the `dir` you pass it: `pear-runtime/corestore`,
  `pear-runtime/next`, and `app-storage`. The paths are visible to anyone who reads the folder.
  Pear's own platform directory is `%APPDATA%\pear` or `%LOCALAPPDATA%\pear` on Windows and
  `~/.config/pear` on Linux.

## 1. Electron / Chromium on disk

### 1.1 Where things live

- `app.getPath('userData')` is for "your app's configuration files". `sessionData` is for "data
  generated by `Session`, such as localStorage, cookies, disk cache". Electron says that by
  default it "points to `userData`" and warns "Chromium may write very large disk cache here". You
  must set it before `ready`. Other names: `temp`, `logs`, `crashDumps`, `recent` (Windows).
  Source: https://www.electronjs.org/docs/latest/api/app (no date on the page).
- In Electron's path provider, `DIR_SESSION_DATA` defaults to `DIR_USER_DATA`. `DIR_CRASH_DUMPS`
  is `userData/Crashpad`. `DIR_APP_DICTIONARIES` is `sessionData/Dictionaries`. On POSIX the
  user cache goes under the OS cache dir (`~/.cache/<app>` on Linux); on Windows it goes under
  Roaming AppData.
  Source: https://github.com/electron/electron/blob/main/shell/common/electron_paths.cc (main).
- `Local State` is written at `sessionData/Local State`. It is a JSON pref store that also holds
  window states and the os_crypt key prefs.
  Source: https://github.com/electron/electron/blob/main/shell/browser/browser_process_impl.cc (main).
- A `persist:<name>` session lives at `sessionData/Partitions/<name>`. A named in-memory session
  gets **no** `Partitions/` subfolder: its path is the `sessionData` root.
  Source: https://github.com/electron/electron/blob/main/shell/browser/electron_browser_context.cc
  (last commit 2026-11-18).
- Chromium's own docs say that on Linux the cache moves to `~/.cache/...`, while on Windows the
  cache dir equals the profile dir.
  Source: https://chromium.googlesource.com/chromium/src/+/main/docs/user_data_dir.md (main).

### 1.2 Per-partition vs global, and what an in-memory session avoids

| Item | Scope | Written by in-memory (non-`persist:`) session? | Evidence |
|---|---|---|---|
| Cookies, `Network Persistent State`, `TransportSecurity`, `Trust Tokens`, HTTP `Cache/`, `Network/` | per partition | **No**: Electron sets these file paths only `if (!in_memory)` | electron `shell/browser/net/network_context_service.cc` (main) |
| `Shared Dictionary/` | per partition | **No**: `shared_dictionary_directory` is set only `if (!is_in_memory())` | chromium `content/browser/storage_partition_impl.cc` (main) |
| `IndexedDB`, `Cache Storage`, `Service Worker`, notification DB | per partition | **No**: `path = is_in_memory() ? FilePath() : partition_path_` | same |
| `Local Storage`, `Session Storage` | per partition | **No**: DOM storage takes `GetStoragePartitionPath()`, which returns `nullopt` in memory | same, plus `dom_storage_context_wrapper.cc` (main) |
| `Code Cache` (JS/Wasm) | per partition | **No**: source comment: "For Incognito mode, we should not persist anything on the disk so we do not create a code cache." | `storage_partition_impl.cc` (main) |
| `WebStorage`/quota, File System, CDM (`CdmStorage.db`), ProtoDB | per partition | **No**: each gets `is_in_memory()` or an empty path | same |
| `blob_storage/` (large blobs paged to disk) | per profile | **No**: the file task runner, and with it disk paging, exists only `if (!context->IsOffTheRecord())`. Electron's `IsOffTheRecord()` returns `in_memory_` | chromium `content/browser/blob_storage/chrome_blob_storage_context.cc`; electron `electron_browser_context.cc` |
| `GPUCache`, `DawnWebGPUCache`, `DawnGraphiteCache` | per partition | **No**: set up only `if (!GetBrowserContext()->IsOffTheRecord() ...)` | chromium `render_process_host_impl.cc`, `gpu/ipc/common/gpu_disk_cache_type.cc` (main) |
| `ShaderCache`, `GrShaderCache`, `GraphiteDawnCache`, `GPUPersistentCache` | **global** (`sessionData` root) | **Yes, shared by every session**. The factory is process-wide and has no off-the-record branch | chromium `content/browser/gpu/gpu_disk_cache_factory.cc`; electron `electron_browser_client.cc` (`GpuCacheDirectory` under `DIR_SESSION_DATA`) |
| `Preferences` | per browser context | **Yes, and it is the default session's file** [inference]. `InitPrefs()` builds a `JsonPrefStore` at `GetPath()/Preferences` with no `in_memory` check, and in memory `GetPath()` is the `sessionData` root | `electron_browser_context.cc` (2026-11-18) |
| `Local State` | global | Yes, app-wide | `browser_process_impl.cc` |
| `Dictionaries/` (hunspell `.bdic`) | global | Yes, if spellcheck downloads a dictionary. "By default Electron will download hunspell dictionaries from the Chromium CDN" (not on macOS) | Electron session docs; `electron_paths.cc` |
| `Crashpad/` | global | Only after `crashReporter.start()` in the main process (see 1.4) | `electron_main_delegate.cc` (main) |
| `electron_debug.log` / `--log-file` | global | Only with `--enable-logging=file` / `ELECTRON_ENABLE_LOGGING` | Electron command-line switches docs |
| `--log-net-log=path` | global | Only if passed | same |
| Extensions prefs | per context | No: skipped `if (!in_memory_)` | `electron_browser_context.cc` |
| Zoom levels | per partition | No: `CreateZoomLevelDelegate` returns nothing when off the record | same |

The `Preferences` row needs a closer look. The prefs registered there include the file dialog's last
directory (`kSelectFileLastDirectory`), the download directory, DevTools file-system paths, the
media-device-ID salt, and spellcheck settings. So an in-memory site that opens a file picker could
leave the **folder it browsed** in the default session's `Preferences` file. It may also share the
default session's media-device-ID salt (a cross-session link) [inference, not tested]. Fix: give
hidden identities their own `sessionData`, or use `session.fromPath()` to point an in-memory session
at a path inside the vault. Then test by diffing the `Preferences` file before and after a session.

Electron's API also says `ses.getStoragePath()` returns `null` "for in memory sessions", and
`addWordToSpellCheckerDictionary` "will not work on non-persistent (in-memory) sessions".
Source: https://www.electronjs.org/docs/latest/api/session (no date).

### 1.3 Known leaks of in-memory / incognito mode and the switches

- **GPU shader cache.** This is global, as the table shows. Chromium's
  `IsShaderDiskCacheEnabled()` returns false when `--disable-gpu-shader-disk-cache` is on the
  command line. That turns off all the global shader caches at once.
  Source: chromium `gpu/config/gpu_finch_features.cc`, `gpu/config/gpu_switches.cc` (main).
  Electron's helper also treats an empty `DIR_SESSION_DATA` as "caching being disabled".
  Shader blobs are keyed by shader source, so a site's custom WebGL shaders could in theory
  show that the site was visited [inference].
- **DNS.** Chromium's host cache is in memory. `ses.clearHostResolverCache()` clears it. The
  Windows DNS Client service keeps its own OS-wide cache, which an app can't control
  [unverified: no Microsoft page read]. HyperBrowser's P2P traffic goes over HyperDHT, not DNS, so
  this mostly affects any normal web fetches.
- **Crashpad.** On Windows and macOS the main process waits for JS to call
  `crashReporter.start()`. Child processes start a Crashpad client at boot (source comment in
  `shell/app/electron_main_delegate.cc`, main). Electron's docs say reports are stored under
  `app.getPath('crashDumps')` even with `uploadToServer: false`, and that "The crash reporter
  cannot be disabled once started".
  Source: https://www.electronjs.org/docs/latest/api/crash-reporter (no date).
  I did not test whether a child crash with no `start()` writes anything [unverified].
  Separately, Windows WER LocalDumps writes to `%LOCALAPPDATA%\CrashDumps` but is "not enabled
  by default" and needs admin rights.
  Source: https://learn.microsoft.com/en-us/windows/win32/wer/collecting-user-mode-dumps
  (ms.date 2024-07-18). On Windows, not shipping `electron_wer.dll` opts out of Electron's WER
  helper (crash-reporter docs).
- **Blob storage.** No spill to disk in memory (table above).
- **Other switches.** `--disk-cache-size`, `--disable-http-cache`, and `--log-file` are documented
  at https://www.electronjs.org/docs/latest/api/command-line-switches (no date). An in-memory
  session doesn't need them, but they help keep `persist:` sites small.
- **Redirecting paths.** `app.setPath('sessionData' | 'crashDumps' | 'temp' | 'logs', ...)` must
  run before `ready`; `sessionData` "before the `ready` event". For full containment, point
  `sessionData` and `crashDumps` at a folder inside the encrypted vault. Note that `userData` and
  `Local State` hold app-wide state that exists before the vault is unlocked.

### 1.4 Tor Browser's approach ("Disk Avoidance")

The design requirement: "should not write any information that is derived from or that reveals
browsing activity to the disk", unless the user opts in to history. Tor Browser does this as
follows:

- Private Browsing is on by default (`browser.privatebrowsing.autostart`).
- `media.cache_size` is 0, because HTML5 video went to the OS temp dir even in Private Browsing.
- The certificate store is in memory (`security.nocertdb`).
- A patch stops the web console writing to `/tmp`.
- Extra prefs turn off the disk cache and offline cache as defense in depth.
- Leaks are tracked under a `tbb-disk-leak` tag.

Swap is explicitly out of scope; the doc leaves it to the OS (for example encrypted swap).
OS-caused exceptions "must be removed by an uninstaller".
Source: https://2019.www.torproject.org/projects/torbrowser/design/ (draft dated 2018-06-15;
the current Tor Browser may differ [unverified]).

What HyperBrowser can borrow: in-memory by default for hidden identities, one checklist of known
leaks, and a bug label for disk leaks.

### What no app can avoid (all OSes)

- That HyperBrowser is installed and ran: Prefetch, Amcache, launcher history.
- Total network bytes per app: SRUM.
- RAM copied to swap, pagefile, or hiberfil.
- Crash metadata the OS keeps.
- Full-disk encryption is the only real answer. The app should say so in its threat model.

## 4. Pear / Holepunch runtime

- Pear v3 removed `pear run` and the `global.Pear` API. `Pear.config` is gone, and the docs point
  to `Pear.app.storage` ("Application storage path"), without saying how it is derived.
  Sources: https://docs.pears.com/reference/pear/api.html , https://docs.pears.com/reference/pear/cli.html
  (both undated, CLI page documents Pear 3.7.0).
- **Embedded in Electron (`pear-runtime`)** writes only under `opts.dir`. That is
  `dir/pear-runtime/corestore` for OTA update cores, `dir/pear-runtime/next/<id>` for staged
  updates, and `dir/app-storage`, the suggested app storage (`pear.storage`, override with
  `opts.storage`). `applyUpdate` swaps the app files next to the bundle (`<base>-<version><ext>`).
  `pear.clearUpgradeDrive()` frees the cached upgrade data. You can pass your own `store`/`swarm`.
  Sources: https://github.com/holepunchto/pear-runtime (README and index.js, last commit
  2026-11-18); https://github.com/holepunchto/pear-runtime-updater index.js (main).
- **Platform directory** (standalone Pear CLI): on Windows, `%USERPROFILE%\AppData\Roaming\pear`
  if it exists, otherwise `%LOCALAPPDATA%\pear`. On Linux, `~/.config/pear`. On macOS,
  `~/Library/Application Support/pear`. Embedded, it falls back to a `pear` dir beside the
  module. It holds `pear.log`, the platform corestore, and a DHT known-nodes cache that
  `pear data dht` exposes.
  Source: https://github.com/holepunchto/pear/blob/main/constants.js (last commit 2026-11-18).
  The DHT cache is a list of peers seen, which is a small network trace.
- **Android (`pear-mobile`)**: `dir` "Defaults to devices standard persistant dir". `storage` is
  optional. Source: https://github.com/holepunchto/pear-mobile README (main).
- **Visibility**: the paths are plain folders. Anyone with access to the user account sees that
  Pear and the app exist and roughly how big their data is. The update corestore reveals only the
  app's own release history, not identities. Keep hidden-identity Corestores inside the vault, not
  in `app-storage`, unless `app-storage` itself sits in the vault.

## Suggested checklist for HyperBrowser (for the design, not done here)

1. Run hidden identities in non-`persist:` sessions **plus** their own in-vault path
   (`session.fromPath(vaultDir)` or a separate `sessionData`), so `Preferences` doesn't land in
   the shared file.
2. `app.commandLine.appendSwitch('disable-gpu-shader-disk-cache')` when any hidden identity can
   open.
3. Never call `crashReporter.start()` (or point `crashDumps` into the vault). No
   `--enable-logging`. Keep the app's own log free of identity keys, or put it in the vault.
4. No OS notifications, recent docs, jump-list entries, or native file dialogs for hidden
   identities. Set the clipboard exclusion format. `setContentProtection(true)` on hidden windows.
5. Android: `allowBackup=false` plus `dataExtractionRules`, `FLAG_SECURE`, no-personalized-learning
   on inputs, strip logs.
6. Write a test that runs a hidden session and diffs every file under `userData`, `sessionData`,
   the cache dir and the temp dir before and after. That is the only way to confirm the
   inferences above.
